# 判断とその理由

設計を変える前に読む。「採用しなかった案」は実際に試した、または検討して不採用にしたもので、同じ問題が再発しない限り試し直さない。

## 実装の土台

### C++ と素の Win32 API で作る
- 理由: 常駐アプリなので軽さを最優先にした。ランタイム不要の単一 exe になる。
- 採用しなかった案: .NET / WinUI 3(ランタイムだけで数十 MB)、C# + NativeAOT(約 15MB。開発は速いが重い)。

### IME の状態は `WM_IME_CONTROL` で問い合わせる
- 理由: 他のプロセスの IME 状態を読める方法がこれしか無い。Microsoft IME、Google 日本語入力で動く。
- 採用しなかった案: TSF の Compartment API(自プロセス内でしか読めない)。
- 注意: IME をオフにしても変換モードの NATIVE ビットは立ったままなので、必ず ON/OFF を先に見る。

### 描画は Direct2D/DirectWrite のソフトウェア描画 + `UpdateLayeredWindow`
- 理由: 角丸のアンチエイリアス、影、半透明、きれいな文字を 1 枚の画像で表せる。小さい画像なので GPU は使わず、D3D デバイスを作らない分メモリが軽い。
- 採用しなかった案: GDI(角がギザギザ、文字の透明度を扱えない)、Direct2D のエフェクトによるぼかし影(デバイスコンテキストが必要で重くなる)。
- 未検討の案: DWM のアクリル背景(`DWMSBT_TRANSIENTWINDOW`)。クリック透過との両立が課題([roadmap.md](roadmap.md))。

## 入力位置の取得

### 基準は「マウスカーソル」ではなく「テキストキャレット」
- 理由: 利用者の要望。取れないアプリでは、IME 切り替えの直後だけマウスの位置に出す。

### Win32 → MSAA → UIA の順に試す
- 理由: アプリによって公開方法が違い、正確さと負荷も違う。軽くて正確なものから試す。

### Chromium/Electron では UIA を使わない
- 理由: Chrome のアドレスバーでは UIA の値が更新されず、Electron アプリでは数十〜百数十 px ずれた。MSAA なら ±1px で一致した。

### Win32 で取れたウィンドウでは、キャレットが消えても最後の位置に出し続ける
- 理由: メモ帳は約 10 秒操作がないと、フォーカスを保ったままシステムキャレットを破棄する。何もしないと、インジケーターが消えるか UIA に切り替わる(UIA は行の高さ全体を返すので、位置が約 20px 上にずれる)。
- Chromium(MSAA)には適用しない。入力欄から離れたときも同じ症状になり、区別できないため。

### UIA で覚えた入力欄でも、毎回 Win32 を先に確かめる
- 理由: 開いた直後のメモ帳はキャレットが無く、UIA で取れてしまう。以後ずっと UIA のままだと、位置がずれ、負荷も高くなる不具合があった。

## 負荷対策

### キャレットの通知は、フォーカスのあるアプリからだけ受け取る
- 理由: システム全体から受けると、無関係なウィンドウの移動・表示の通知が毎秒 100 件以上届き、負荷の大半を占めていた。フォーカスが変わるたびにフックを付け替える。

### 入力が無い間は問い合わせを減らす(`GetLastInputInfo`)
- 理由: IME の切り替えもキャレットの移動も、ほぼキー操作かマウス操作が起点になる。

### タイマーは 100ms のまま間引かない
- 採用しなかった案: 入力が無い間はタイマーを 1 秒にする。半角/全角キーを押してから反映までが最大 1 秒遅れた。

### キーボードのフックや Raw Input は使わない
- 理由: 全キー入力を受け取る仕組みは、セキュリティソフトにキーロガーとして警戒されるおそれがある。`WH_KEYBOARD_LL` はさらに、システム全体の入力遅延の原因にもなる。
- 代わりに、100ms ごとの確認と `GetLastInputInfo` で間に合わせている。

## 表示と見た目

### 既定の表示モードは「入力欄にいる間は常に表示」
- 理由: 開発中ずっとこの動きで使っており、利用者の要望でもあった。「切り替えたときだけ表示」のほうが軽いが、既定にはしなかった。

### 「a」には濃い枠を付ける
- 理由: 暗い背景色だけでは、暗いアプリの上で見分けにくいという指摘があった。Fluent の ControlStrongStroke 相当の枠を付け、ダークの背景も少し明るくした。

### 「あ」はテーマに応じたアクセントの濃淡を使う
- 理由: Fluent の決まり(ライトは濃いアクセントに白文字、ダークは明るいアクセントに黒文字)に合わせ、Windows 11 の他の部品と調和させる。

## 配布

### コード署名をしない zip で配る
- 理由: 費用をかけずに配るため。初回起動時に SmartScreen の警告が出るので、README で対処とハッシュの確認方法を案内する。
- 無料で署名する方法として、Microsoft Store(個人の開発者登録は無料。MSIX 化と、自動起動をスタートアップタスクに変える改修が必要)と、SignPath Foundation(オープンソースが条件。発行元は SignPath Foundation になる)がある([roadmap.md](roadmap.md))。

### `uiAccess` は使わない(スタートメニューの上には表示しない)
- 理由: 信頼された証明書での署名と、Program Files への配置が必要。費用がかかり、zip を展開するだけの配布もできなくなる。権限が強くなる(管理者権限のアプリも操作できる)ため、不具合のときの影響も大きい。
- 使えば、スタートメニューの上への表示と、管理者権限のアプリでの IME 判定ができる見込み。

### 著作権者は個人名を出さず「KanaCaret contributors」とする
- ライセンスは MIT。

### 名前は「KanaCaret」
- 理由: 旧名「IME インジケーター」(ime-indicator)は、GitHub に同名のリポジトリが 7 つあり、同じ目的の日本のプロジェクトもあって混同されやすかった。「かな」+「キャレット」で何をするかが伝わり、GitHub に同名も似た名前も無かった。
- 他に検討した候補: Kanaret、ImeGlance、KanaBadge、ImePip、ImeBadge、ImeLamp。
- 確かめたのは GitHub のリポジトリ名だけで、商標や Microsoft Store の名前は調べていない。ストアで配るときは、そのときに名前を確保する。
- PC 内で共有される名前(Mutex、ウィンドウクラス)には持ち主名を含めて、同じ名前の別アプリと重ならないようにした。
