# 判断とその理由

設計を変える前に読む。「採用しなかった案」は実際に試した、または検討して不採用にしたもので、同じ問題が再発しない限り試し直さない。

## 実装の土台

### C++ と素の Win32 API で作る
- 理由: 常駐アプリなので軽さを最優先にした。ランタイム不要の単一 exe になる。
- 採用しなかった案: .NET / WinUI 3(ランタイムだけで数十 MB)、C# + NativeAOT(約 15MB。開発は速いが重い)。

### IME の状態は `WM_IME_CONTROL` で問い合わせる
- 理由: 他のプロセスの IME 状態を読める方法がこれしか無い。Microsoft IME、Google 日本語入力で動く。
- 採用しなかった案: TSF の Compartment API(自プロセス内でしか読めない)。
- 注意: IME をオフにしても変換モードの NATIVE ビットは立ったままなので、必ず ON/OFF を先に見る。

### 描画は Direct2D/DirectWrite のソフトウェア描画 + `UpdateLayeredWindow`
- 理由: 角丸のアンチエイリアス、影、半透明、きれいな文字を 1 枚の画像で表せる。小さい画像なので GPU は使わず、D3D デバイスを作らない分メモリが軽い。
- 採用しなかった案: GDI(角がギザギザ、文字の透明度を扱えない)、Direct2D のエフェクトによるぼかし影(デバイスコンテキストが必要で重くなる)。
- 未検討の案: DWM のアクリル背景(`DWMSBT_TRANSIENTWINDOW`)。クリック透過との両立が課題([roadmap.md](roadmap.md))。

## 入力位置の取得

### 基準は「マウスカーソル」ではなく「テキストキャレット」
- 理由: 利用者の要望。

### 入力位置が分からないときは表示しない
- 理由: 利用者の要望。入力位置と関係のない場所(マウスの位置)に出るより、出ないほうが分かりやすい。
- 採用しなかった案: IME 切り替えの直後 1.5 秒だけマウスの位置に出す(以前の動き。設定でオフにできた)。設定ごと廃止した。

### Win32 → MSAA → UIA の順に試す
- 理由: アプリによって公開方法が違い、正確さと負荷も違う。軽くて正確なものから試す。

### Chromium/Electron では UIA を使わない
- 理由: Chrome のアドレスバーでは UIA の値が更新されず、Electron アプリでは数十〜百数十 px ずれた。MSAA なら ±1px で一致した。

### Win32 で取れたウィンドウでは、キャレットが消えても最後の位置に出し続ける
- 理由: メモ帳は約 10 秒操作がないと、フォーカスを保ったままシステムキャレットを破棄する。何もしないと、インジケーターが消えるか UIA に切り替わる(UIA は行の高さ全体を返すので、位置が約 20px 上にずれる)。
- Chromium(MSAA)には適用しない。入力欄から離れたときも同じ症状になり、区別できないため。

### UIA で覚えた入力欄でも、毎回 Win32 を先に確かめる
- 理由: 開いた直後のメモ帳はキャレットが無く、UIA で取れてしまう。以後ずっと UIA のままだと、位置がずれ、負荷も高くなる不具合があった。

## 負荷対策

### キャレットの通知は、フォーカスのあるアプリからだけ受け取る
- 理由: システム全体から受けると、無関係なウィンドウの移動・表示の通知が毎秒 100 件以上届き、負荷の大半を占めていた。フォーカスが変わるたびにフックを付け替える。

### 入力が無い間は問い合わせを減らす(`GetLastInputInfo`)
- 理由: IME の切り替えもキャレットの移動も、ほぼキー操作かマウス操作が起点になる。

### タイマーは 100ms のまま間引かない
- 採用しなかった案: 入力が無い間はタイマーを 1 秒にする。半角/全角キーを押してから反映までが最大 1 秒遅れた。

### キーボードのフックや Raw Input は使わない
- 理由: 全キー入力を受け取る仕組みは、セキュリティソフトにキーロガーとして警戒されるおそれがある。`WH_KEYBOARD_LL` はさらに、システム全体の入力遅延の原因にもなる。
- 代わりに、100ms ごとの確認と `GetLastInputInfo` で間に合わせている。

## 表示と見た目

### ウィンドウの移動中・サイズ変更中は隠す
- 理由: 入力位置の問い合わせはウィンドウの動きに追いつかず(通知はまとめ、UIA は非同期)、インジケーターが遅れてかくつきながら付いていく。移動の間は入力しないので、隠しても困らない。
- 判定は `GUITHREADINFO` の `GUI_INMOVESIZE` で行い、`EVENT_SYSTEM_MOVESIZESTART/END` は `Update()` を呼ぶきっかけにだけ使う。終了の通知を取りこぼしても、100ms ごとの確認で表示が戻る。
- 採用しなかった案: 移動中も位置を追い続ける(問い合わせを増やすと負荷が上がり、それでも描画の遅れは残る)。

### 「入力中は隠す」は、入力の時刻とマウスカーソルの位置で判定する
- 理由: 利用者の要望(入力中は文字で日本語か英語か分かる)。キー入力だけを知る仕組みはフックか Raw Input しか無く、使わない方針(上の「キーボードのフックや Raw Input は使わない」)。`GetLastInputInfo` はマウスの操作でも進むので、カーソルが動いていないときだけキー入力とみなす。
- 弱点: その場でのクリックやホイールもキー入力に数える。隠れるのは 1 秒だけなので許容した。
- キーやボタンを離したときも入力の時刻が進むので、IME の切り替えとフォーカスの移動から 300ms の入力は数えない。数えると、クリックで入力欄を移るたびに約 0.8 秒表示が遅れた。
- 採用しなかった案: `GetLastInputInfo` だけで判定する(マウスを動かすたびに隠れる)。キャレット移動の通知で判定する(通知の来ないアプリ(UIA で取るアプリ)で効かず、隠している間は入力位置を問い合わせない作りとも合わない)。
- 表示モードの 4 つ目にはせず、チェックボックスにした。「日本語入力のときだけ表示」などと組み合わせられるようにするため。

### 既定の表示モードは「入力欄にいる間は常に表示」
- 理由: 開発中ずっとこの動きで使っており、利用者の要望でもあった。「切り替えたときだけ表示」のほうが軽いが、既定にはしなかった。

### 「a」には濃い枠を付ける
- 理由: 暗い背景色だけでは、暗いアプリの上で見分けにくいという指摘があった。Fluent の ControlStrongStroke 相当の枠を付け、ダークの背景も少し明るくした。

### 「あ」はテーマに応じたアクセントの濃淡を使う
- 理由: Fluent の決まり(ライトは濃いアクセントに白文字、ダークは明るいアクセントに黒文字)に合わせ、Windows 11 の他の部品と調和させる。

## 設定画面

### 素の Win32 の標準コントロールで作る
- 理由: 設定画面のためだけにランタイムを持ち込まない。標準のコントロールなら、キーボード操作と読み上げソフトへの対応が付いてくる。exe は約 60KB 増えた(設定画面とダーク表示を合わせて)。
- 採用しなかった案: WebView2 / WinUI 3(ランタイムが数十 MB で、軽さ最優先に反する)、部品をすべて Direct2D で描く(Fluent の見た目にそろえられるが、コードが 2〜3 倍になり、キーボード操作と UIA プロバイダーを自分で作る必要がある)。

### 設定画面はアプリのテーマ(ライト/ダーク)に合わせる
- 理由: 利用者の要望。ダークのテーマで明るい画面が開くとまぶしい。
- 標準のコントロールをダークにするには、公開されていない uxtheme の関数(`SetPreferredAppMode` など)が必要になる。他のアプリでも使われている方法で、序数で呼ぶ。序数の意味が分かっているビルド(18362 以上)で、4 つとも見つかったときだけ使い、それ以外はライトのまま表示する。将来の Windows で動かなくなっても、ライトの表示に戻るだけにする。
- チェックボックスとスライダーには標準のダーク表示が無いので、NM_CUSTOMDRAW で描く。標準の部品のまま描くので、キーボード操作と読み上げソフトへの対応は残る。
- コンボボックスは `DarkMode_CFD` で閉じた欄はダークになるが、開いた一覧の選んでいる行が白地に白い文字になって読めなかった。一覧の行を `CBS_OWNERDRAWFIXED` で描くと、閉じた欄が白い枠と箱の付いた矢印の古い形に変わるので、閉じた欄もサブクラスで描く。
- 採用しなかった案: タイトルバーだけをダークにする(中身との差が目立つ)、部品をすべて自前で描く(上の「素の Win32 の標準コントロールで作る」と同じ理由)。

### 変更はすぐ反映し、OK / キャンセルを置かない
- 理由: Windows 11 の設定アプリと同じ動き。プレビューで結果が見えるので、取り消しのための仕組みは要らないと判断した。

### 色は背景色だけを選んでもらう
- 理由: 文字色と枠まで選べると、読めない組み合わせを作れてしまう。文字は明るさから白か黒を選び、枠は自動で付ける。
- 「a」と「あ」で別々に選べる。ライトとダークで別の色にはしない(項目が倍になり、分かりにくい)。

### 通知領域のメニューは「設定...」「一時停止」「終了」だけにする
- 理由: メニューに全部の設定を並べると長くなり、大きさや色は選んでも結果が見えない。
- 「○○.exe では表示しない」も、利用者の要望で廃止した。メニューを開く直前に使っていたアプリがエクスプローラー(タスクバー)になりやすく、意図しない名前が出る。表示するアプリは設定画面の「アプリ」で選ぶ。

### 除外するアプリではなく、表示するアプリを選ぶ(「すべてのアプリ」も選べる)
- 理由: 利用者の要望。表示したいアプリが限られているとき、除外するアプリを 1 つずつ足すより、表示するアプリを選ぶほうが手順が少ない。
- 除外と対象の両方を持つと、どちらが優先か分かりにくくなるので、除外の設定は削除した(以前の除外の設定は引き継がない)。
- 「すべてのアプリ」のときに一覧でチェックを付けたら、「チェックしたアプリだけ」に切り替える。先に切り替えてからチェックする手順を省くため。

### アプリは、実行中のアプリの一覧にチェックを付けて選ぶ
- 理由: exe 名を手で打つより手順が少なく、名前を間違えない。対象にしたいアプリを開いておけば、設定画面でチェックを付けるだけで済む。
- 採用しなかった案: exe 名を入力して追加する欄と、最後に使ったアプリを追加するボタン(以前の除外の画面)。入力の手間があり、ボタンは直前のアプリしか選べない。
- 採用しなかった案: 通知領域のメニューに実行中のアプリを並べる。メニューは「設定...」「一時停止」「終了」だけにする方針(上)に反し、選ぶたびにメニューが閉じる。

### 通知領域のアイコンは exe のアイコンにする
- 理由: 利用者の要望。アプリのアイコンと見た目をそろえ、何のアプリかを分かりやすくする。IME の状態はインジケーターで分かる。
- 採用しなかった案: いまの IME 状態のバッジを描く(以前の動き)。

## 配布

### コード署名をせず、インストーラーと zip の両方で配る
- 理由: 費用をかけずに配るため。初回起動時に SmartScreen の警告が出るので、README で対処とハッシュの確認方法を案内する。
- インストーラーは、スタートメニューへの登録、「設定 > アプリ」からのアンインストール(起動中のアプリの終了と自動起動の削除を含む)、上書きでのバージョンアップのために用意した。インストールしたくない人のために zip も残す。

### インストーラーは NSIS で作り、利用者ごとに入れる
- 道具は NSIS 3(利用者の選択)。スクリプト 1 本(`installer/KanaCaret.nsi`)で作れ、日本語の画面が標準で入っている。
- 入れる先は `%LOCALAPPDATA%\Programs\KanaCaret`、登録は HKCU だけ。管理者権限(UAC)を求めずに入れられ、自動起動(HKCU の Run キー)とも範囲がそろう。
- 起動中のアプリは、非表示のメインウィンドウ(クラス名 `HectareBase.KanaCaret.Main`)に `WM_CLOSE` を送って終わらせる。アプリに終了用の引数を足さずに済み、通常の「終了」と同じ後始末になる。
- アンインストールでは、Run キーの値がインストール先の exe を指しているときだけ消す(zip 版を登録していれば残す)。設定フォルダーは尋ねてから消し、サイレント(`/S`)のときは残す。
- 採用しなかった案: Inno Setup(同程度に作れるが、利用者が NSIS を選んだ)、WiX で MSI(記述が多く .NET SDK も要る)、Program Files に全ユーザー向けに入れる(UAC が要る。`uiAccess` を使わない限り利点がない。下の「`uiAccess` は使わない」)。
- 無料で署名する方法として、Microsoft Store(個人の開発者登録は無料。MSIX 化と、自動起動をスタートアップタスクに変える改修が必要)と、SignPath Foundation(オープンソースが条件。発行元は SignPath Foundation になる)がある([roadmap.md](roadmap.md))。

### `uiAccess` は使わない(スタートメニューの上には表示しない)
- 理由: 信頼された証明書での署名と、Program Files への配置が必要。費用がかかり、zip を展開するだけの配布も、管理者権限の要らないインストーラーもできなくなる。権限が強くなる(管理者権限のアプリも操作できる)ため、不具合のときの影響も大きい。
- 使えば、スタートメニューの上への表示と、管理者権限のアプリでの IME 判定ができる見込み。

### 著作権者は個人名を出さず「KanaCaret contributors」とする
- ライセンスは MIT。

### 名前は「KanaCaret」
- 理由: 旧名「IME インジケーター」(ime-indicator)は、GitHub に同名のリポジトリが 7 つあり、同じ目的の日本のプロジェクトもあって混同されやすかった。「かな」+「キャレット」で何をするかが伝わり、GitHub に同名も似た名前も無かった。
- 他に検討した候補: Kanaret、ImeGlance、KanaBadge、ImePip、ImeBadge、ImeLamp。
- 確かめたのは GitHub のリポジトリ名だけで、商標や Microsoft Store の名前は調べていない。ストアで配るときは、そのときに名前を確保する。
- PC 内で共有される名前(Mutex、ウィンドウクラス)には持ち主名を含めて、同じ名前の別アプリと重ならないようにした。
